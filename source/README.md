# Noiee

Noiee is a local Mac workspace for Chat, Agent tasks and project coding, formerly called Saleh Uncensored. The existing installed bundle remains at `~/Applications/Saleh Uncensored.app` to preserve its verified runtime and macOS permission identity. Its windows, menus and app display name are Noiee. The app uses installed Node.js and LM Studio on `127.0.0.1:1234`. It is a personally signed Apple Silicon app for macOS 15.2 or later, rather than a notarized, self-contained distribution.

## Models and access

New chats use the saved local model default. The current preferred model is `qwen3.8-27b-uncensored-hauhaucs-aggressive-mtp`; existing chats, schedules and owner bindings retain their exact selected identities. The model picker distinguishes installed models from loaded instances. Refresh after changing LM Studio. Requests recheck the exact selected instance and its supported mode, reasoning, image input and loaded context. The app does not silently substitute, download or load another model.

Concise and Detailed select response instructions without reasoning; Deep reasoning uses the model's actual reasoning capability. Ordinary responses send `max_tokens: -1` to LM Studio, which removes the prediction-token cap; loaded context, response-size limits, execution deadlines and Stop still apply. This is not unlimited context or a model-quality guarantee. Agent compaction counts conservative UTF8 bytes, includes the actual system/tool envelope and preserves the current request and complete current tool pairs. **Full Access** skips app confirmations for operational tools. The running window title and access chip show the current mode. Full Access does not grant system permissions or inherit Codex's accounts.

## Chat and Agent

Chat supports saved conversations, rename, projects, pins, archive, search, text/image attachments, exports and per-chat drafts. Agent uses the selected local model with bounded plans and tool requests. It records actual results separately from the model's explanation. Background text runs can finish while you browse another workspace; opening the saved result does not replay the request. Two text-only Chats can overlap; Agent and image-bearing Chat need exclusive ordinary-run capacity.

The shared reply parser accepts CR, LF and CRLF event streams across UTF8/network boundaries. Malformed provider text fails before entering durable content. A failed reply retains valid partial evidence and does not prevent an independent subsequent run from saving. Missing terminal outcomes remain visibly incomplete or unconfirmed.

The rail switches between Chat and Tasks. Restoring or selecting a chat reveals its sidebar row once; polling preserves manual scroll. Project labels retain full accessible names and tooltips. The command palette and in-chat search use existing controls and keep the composer draft. A cold Tasks page hides incidental old saved successes from other chats; live runs, unsaved/error outcomes and completions actually observed in that page remain accessible.

## Data, Stop and release verification

Normal Quit saves drafts, drains owned subsystems, checks physical process exit and preserves uncertainty when closure cannot be established. A successful result card or export dialog is not proof of a saved export, clean shutdown or cold-start persistence. Stop can cancel tracked work and revoke pending authority; it cannot undo completed effects or prove that a third-party service did nothing.

Release installation requires normal app closure, stable copied stores, a complete local backup, a signed rollback app and exact reviewed source/package bindings. Verification compares all prior chats, drafts, histories, images, owner/VM records, access settings, schedules and recovery evidence. SQL checks run only on scratch copies of stable closed stores. Native acceptance separately checks a disposable task's actual file/test outcome, its saved receipt, an unsent draft, normal Quit and cold reopen.

The app is not established as full Codex parity or as stronger than Astra. Local model instruction following and coding quality require task-specific evidence; more tokens or aggressive hardware settings are not a substitute for a benchmark. Existing VM startup failures, retained recovery restrictions, provider/account setup and unverified external outcomes stay visible.
